# hermes

The Hermes agent (`hermes-agent` 0.17.0, installed under
`~/.hermes/`) runs on `snoc-beelink` as a pair of **user** systemd
units, not system units:

| Unit                       | Scope | Listens on      |
| -------------------------- | ----- | --------------- |
| `hermes-gateway.service`   | user  | `0.0.0.0:8642`  |
| `hermes-dashboard.service` | user  | `127.0.0.1:9119`|

The unit files themselves live in `~/.config/systemd/user/` and are
generated by the hermes installer, so this folder holds only a drop-in
override rather than a copy of them. `Linger=yes` is set for the
`batesste` user, which is what lets these start at boot with no login
session.

There is also `hermes-webui.service` (a separate `hermes-webui` repo)
on `127.0.0.1:8787`, and the weekly S3 backup timer in
[../backup](../backup).

## Fix 1 — the dashboard was taking port 9119 on every interface

The stock unit passes `--host 0.0.0.0`. That claimed 9119 on the LAN
address and the tailnet address as well as loopback, and tailscaled
needs `100.118.22.104:9119` for its own
`serve :9119 -> 127.0.0.1:9119` entry. tailscaled lost the race on
every boot and retried forever, roughly every 20 s:

```
tailscaled: localListener failed to listen on 100.118.22.104:9119,
            backing off: listen tcp4 100.118.22.104:9119:
            bind: address already in use
```

It did manage to claim the IPv6 tailnet address, so the serve entry
half-worked and the breakage was easy to miss.

[`systemd/user/hermes-dashboard.service.d/override.conf`](./systemd/user/hermes-dashboard.service.d/override.conf)
moves the bind to `--host 127.0.0.1`. This is also what hermes upstream
recommends — `--insecure` is now a documented no-op, and its help text
says to bind loopback and tunnel instead.

It closed a real exposure too. No auth provider is configured, so on
the old `0.0.0.0` bind the dashboard was reachable **unauthenticated**
from any LAN host at `10.0.0.15:9119`.

Install with:

```bash
mkdir -p ~/.config/systemd/user/hermes-dashboard.service.d
cp systemd/user/hermes-dashboard.service.d/override.conf \
   ~/.config/systemd/user/hermes-dashboard.service.d/
systemctl --user daemon-reload
systemctl --user restart hermes-dashboard
```

### Why nginx is now in the path

Moving to loopback trips a second guard. The dashboard enforces a
DNS-rebinding defence (GHSA-ppp5-vxwm-4cf7, `_is_accepted_host` in
`hermes_cli/web_server.py`): on a loopback bind it accepts only
loopback `Host` values, and the WebSocket handshake applies the same
test to `Origin`. A `0.0.0.0` bind disables the guard entirely, which
is the only reason the tailnet path used to work.

`tailscale serve` forwards the tailnet hostname verbatim, so proxying
it straight at 9119 returns:

```
{"detail":"Invalid Host header. Dashboard requests must use the
  hostname the server was bound to."}
```

There is no allowed-hosts setting to configure, so an nginx vhost on
`127.0.0.1:9120` normalises both headers back to loopback, and
`tailscale serve` points at that instead:

```bash
tailscale serve --bg --https 9119 http://127.0.0.1:9120
```

See [nginx/sites-available/hermes-dashboard](../nginx/sites-available/hermes-dashboard).
This does re-permit what the guard blocks. The trade is deliberate: the
guard exists to stop a malicious website rebinding DNS in a victim's
browser, whereas everything reaching that listener has already passed
Tailscale's TLS and tailnet ACLs. Since the dashboard has no auth
provider, tailnet membership is the only thing gating it — the shim
must stay bound to loopback.

## Fix 2 — a duplicate system unit had restarted 140,989 times

`/etc/systemd/system/hermes.service` ran `hermes gateway` as a *system*
unit, duplicating the user-level `hermes-gateway.service`. The user
unit always won the race, so the system one exited immediately every
time:

```
❌ Gateway already running (PID 1469).
```

With `Restart=always` and `RestartSec=10` it had looped **140,989**
times — continuously since the 16 Aug boot. It has never once served
traffic.

It was disabled, not deleted:

```bash
sudo systemctl disable --now hermes.service
```

The unit file is still at `/etc/systemd/system/hermes.service` if it is
ever wanted. It should not be re-enabled while the user units are in
place; `Linger=yes` already covers starting hermes at boot.
